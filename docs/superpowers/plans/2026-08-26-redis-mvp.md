# Redis Support MVP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Detect Redis dependencies in customer repositories, flip Redis from a hard rejection to a supported managed dependency, and provision a private single-node ElastiCache Valkey cache (cache.t4g.micro) in the customer-account ApplicationStack with automatic env-var injection, reuse across redeploys, safe deletion, and runtime failure classification.

**Architecture:** Provider-neutral Redis detection/compatibility lives in `packages/analysis` (deterministic, no AI). Persistence follows the existing `databaseRequired` boolean pattern on `applications` plus a rich `detectedMetadata.redis` JSONB object. AWS specifics (ElastiCache Valkey, subnet group, security group, env injection) live only in `packages/cdk`'s `ApplicationStack`, gated on a new stack prop. IAM additions go through the bootstrap stack with the mandatory `security-details.ts` disclosure lockstep. Runtime failures flow through the existing structured-event failure classifier with two new failure codes.

**Tech Stack:** TypeScript strict, Drizzle ORM/PGlite, Fastify, AWS CDK (`CfnCacheCluster` — no L2 exists), Vitest, Playwright (fixture mode).

## Global Constraints

- Redis profile (spec §3): ElastiCache, engine **valkey**, standalone non-cluster, **1 node**, **cache.t4g.micro**, port **6379**, private networking only. No engine-version pin (AWS default) — matches how RDS pins major version only.
- Explicitly unsupported (spec §4): cluster mode, Redis Stack, RedisJSON, RediSearch, custom modules, TLS (`rediss://`), Serverless ElastiCache, MemoryDB, BYO Redis, public endpoints, custom ports, any Redis tuning UI. Unsupported ⇒ fail during analysis (NOT_COMPATIBLE), never at provisioning.
- Provider-neutral core: `packages/analysis`, `packages/db`, `packages/contracts`, `apps/api`, `apps/web` must say "redis"/"cache", never "elasticache"/"valkey". AWS words appear only in `packages/cdk` and technical-detail copy.
- Confidence policy (spec §7): `high` ⇒ `redisRequired = true`; `medium`/`low` ⇒ false. High = any very-high signal (compose redis service, source-code client initialization) OR ≥2 distinct corroborating signals. Transitive/dev-only/docs-only evidence alone must never provision.
- Never edit `packages/cdk/src/analysis/*` — they are re-export barrels of `packages/analysis/src/*`.
- Enum parity: any change to `packages/db/src/enums.ts` must be mirrored in `packages/contracts/src/index.ts` (parity test exists).
- IAM lockstep: any new action list in `packages/cdk/src/bootstrap/bootstrap-stack.ts` needs a verbatim-matching constant in `apps/web/src/lib/security-details.ts` and coverage in `apps/web/test/security-details.test.ts` (which regex-extracts the CDK source).
- Copy lockstep: new vocabulary goes in `packages/copy-map/src/index.ts` + test; web mirrors in `apps/web/src/lib/deployment-vocabulary.ts`/`diagnostic-vocabulary.ts` are parity-tested by `apps/web/test/copy-map-parity.test.ts`. Top-level labels must stay jargon-free (`JARGON_PATTERN`); do not put "ElastiCache"/"Valkey" in top-level labels ("Redis" is acceptable).
- Failure codes use SCREAMING_SNAKE matching the existing enum (`REDIS_PROVISIONING_FAILED`, `REDIS_CONNECTION_FAILED`), not the spec's lowercase suggestions.
- Event types use dotted-family naming (`redis.*`), not underscores.
- Tags on every new AWS resource: `deployz:component`, `deployz:installation`, `deployz:application`, `deployz:vendor` (same four as existing ApplicationStack resources).
- Cache uses default (Delete) removal policy — NOT `RETAIN` like RDS — so stack deletion removes it (spec §33). A failed redeploy must not touch it (stack updates leave it unchanged).
- Existing non-Redis deployments must synth byte-identical infrastructure (redisRequired=false ⇒ zero ElastiCache resources, zero REDIS_* env vars).
- Out of scope (confirmed absent from codebase): deployment-learning system (spec §36 — does not exist; skip), cost display (spec §32 — no cost system exists; skip), enable/disable toggle, secrets/AUTH for the cache (private networking only, spec §21).
- All commits: conventional prefix (`feat:`, `fix:`, `test:`, `docs:`) + `Co-Authored-By: Claude Fable 5 <noreply@anthropic.com>`.
- Run tests per package with `pnpm --filter <pkg> exec vitest run`; full check = `pnpm build && pnpm vitest run && pnpm lint` (CI runs exactly this; local vitest under-reports CDK tests — trust CI).
- Spec: `docs/redis-mvp-spec.md`. Research notes: `.superpowers/sdd/research/*.md` (read the relevant one before your task).

**Files:**

**Interfaces:**

```ts
export type RedisConfidence = 'high' | 'medium' | 'low';
export type RedisPurpose =
  | 'cache' | 'queue' | 'background_jobs' | 'sessions'
  | 'rate_limiting' | 'locks' | 'broker' | 'unknown';

export interface RedisCompatibility {
  supported: boolean;
  reason?: string;        // set when unsupported, e.g. 'Requires RedisJSON'
}

export interface RedisRequirement {
  required: boolean;              // true ⇔ confidence === 'high' AND compatibility.supported
  confidence: RedisConfidence;
  purposes: RedisPurpose[];       // deduped, ['unknown'] if none identified
  evidence: string[];             // human-readable, e.g. 'bullmq dependency in package.json'
  connectionEnvVars: string[];    // subset of KNOWN_REDIS_ENV_VARS found in repo, in canonical order
  compatibility: RedisCompatibility;
}

export function assessRedis(tree: FileTree): RedisRequirement;

export type RedisEnvBindingKind = 'url' | 'host' | 'port';
export interface RedisEnvBinding { name: string; kind: RedisEnvBindingKind }
// Empty/unknown input → defaults: [{REDIS_URL,url},{REDIS_HOST,host},{REDIS_PORT,port}]
export function resolveRedisEnvBindings(connectionEnvVars: string[]): RedisEnvBinding[];
```

**Detection rules (implement exactly):**

Signals, each contributing one evidence string:
- **Very-high**: docker-compose service using a `redis`/`valkey` image (`docker-compose.yml`, `docker-compose.*.yml`, `compose.yml`, `compose.*.yml` at any depth — match `image:` values containing `redis` or `valkey`); source-code client initialization in `.ts/.js/.mjs/.cjs/.jsx/.tsx/.py/.rb` files (`new Redis(`, `createClient(` with a `redis` import in the same file, `Redis.from_url`, `redis.Redis(`, `Sidekiq.configure`).
- **High**: known Redis env var referenced in `.env.example`/`.env.template`/`.env.sample` (any depth) or in source via `process.env.X` (X in `KNOWN_REDIS_ENV_VARS`, below); Redis-backed job library as a **direct** dependency: npm `bull`, `bullmq`, `@nestjs/bull`, `@nestjs/bullmq` (in `dependencies` of any non-ignored `package.json`, workspace-aware like existing `checkRedis`); Python `celery` together with a `redis`-ish broker signal, `rq`, `django-redis` in `requirements.txt` or `pyproject.toml`; Ruby `sidekiq` in `Gemfile`.
- **Medium**: direct Redis client dependency alone — npm `redis`/`ioredis`/`@redis/client` in `dependencies`; Python `redis` line in `requirements.txt`/`pyproject.toml`; Ruby `redis` gem; Go `github.com/redis/go-redis` or `github.com/go-redis/redis` in `go.mod`; PHP `predis/predis` in `composer.json` `require`.
- **Low only**: dependency only in `devDependencies`; README mention; nothing else. Lockfiles are never inspected (avoids transitive false positives).

Confidence: `high` if any very-high signal OR ≥2 distinct signals from {high, medium} buckets; `medium` if exactly one high or medium signal; `low` otherwise.

`KNOWN_REDIS_ENV_VARS` (canonical order): `REDIS_URL`, `REDIS_URI`, `REDIS_HOST`, `REDIS_PORT`, `REDIS_PASSWORD`, `CACHE_URL`, `QUEUE_REDIS_URL`, `CELERY_BROKER_URL`, `CELERY_RESULT_BACKEND`. Collect into `connectionEnvVars` when referenced in env-sample files or `process.env` usage. `CACHE_URL`/`CELERY_*` count only when their sample value starts with `redis://` or `rediss://` or the file also has other redis evidence.

Purposes: `bull|bullmq|@nestjs/*` → `queue`; `sidekiq|rq` → `background_jobs`; `celery` → `broker`; `django-redis` → `cache`; `connect-redis` → `sessions`; none → `['unknown']`.

Compatibility — unsupported (first match wins, sets `reason`):
- deps `@redis/json`, `@redis/search`, `redis-om`, python `redisearch`/`rejson` → "Requires Redis Stack modules (RedisJSON/RediSearch), which Deployz does not support."
- compose image containing `redis-stack` → same reason.
- cluster usage: `new Redis.Cluster(`, `createCluster(`, `RedisCluster(`, `CLUSTER SLOTS` → "Requires Redis Cluster, which Deployz supports only in standalone mode." (word it: "Requires Redis Cluster mode, which Deployz does not support.")
- `rediss://` anywhere in env samples or source → "Requires TLS (rediss://) connections, which Deployz's managed Redis does not provide."
Otherwise `supported: true` (unknown ⇒ supported, spec §10).

`resolveRedisEnvBindings`: `REDIS_URL|REDIS_URI|CACHE_URL|QUEUE_REDIS_URL|CELERY_BROKER_URL|CELERY_RESULT_BACKEND` → `url`; `REDIS_HOST` → `host`; `REDIS_PORT` → `port`; `REDIS_PASSWORD` → skipped (no auth in MVP). Result preserves canonical order, deduped. Empty input → the three defaults above.
