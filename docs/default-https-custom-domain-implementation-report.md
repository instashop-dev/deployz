# Default HTTPS + Custom Domain — Implementation Report

Final report for the MVP plan "Default HTTPS + Existing Custom Domain Upgrade".

## Executive Summary

Every deployment now has a permanent, deterministic HTTPS address
`https://d-<deployment-id>.deployz.dev`. The permanent address is reconciled
against the production Cloudflare zone `deployz.dev` through an injectable,
namespace-guarded DNS client; a deployment reaches READY on
default-HTTPS verification + application health alone; the existing custom
domain flow is preserved and promotes to the preferred URL only when ACTIVE
(ACTIVE already requires DNS validity, an issued certificate, and a successful
HTTPS probe); every failure path falls back to the permanent default URL;
delete/purge reconciles DNS teardown including orphaned records; watchdogs
bound provider retries.

Implementation confidence is high. The work was a delta over the existing
default-HTTPS/custom-domain machinery (audit finding, Phase 0), every phase
was PR-reviewed, CI-verified on two matrices (Test and build; Simulated E2E),
and merged; the simulated provider E2E suite found and fixed two latent bugs
before merge.

## Architecture

- **defaultUrl** — `https://d-<deployment-id>.deployz.dev`, generated by
  `getDefaultDeploymentHostname`/`getDefaultDeploymentUrl`
  (`apps/api/src/default-https.ts`): deterministic, lower-cased, DNS-safe id
  validation, reserved names (`deployz.dev`, `app/www/api/admin.deployz.dev`)
  protected by `assertMutableDefaultHostname`.
- **customUrl** — the existing custom-domain flow (relay ACM + ALB listeners,
  customer DNS), unchanged in mechanism; promoted only when ACTIVE.
- **preferredPublicUrl** — `resolveAppUrl` (`apps/api/src/fleet-row.ts`):
  custom URL only when ACTIVE (which requires DNS valid + cert ISSUED + HTTPS
  probe success inside the machine); otherwise the default-HTTPS URL; ALB
  endpoint as last fallback. `resolveProbeUrl` derives from the same function,
  so the relay probes exactly what the customer sees. `GET
  /api/deployments/:id` exposes `defaultUrl` next to `appUrl`.
- **Cloudflare provider abstraction** — `apps/api/src/cloudflare-records.ts`:
  `CloudflareDnsClient` (`getRecord`, `upsertDefaultDeploymentRecord`,
  `deleteDefaultDeploymentRecord`, validation-record variants,
  `listDefaultRecords`) with injectable HTTP transport, search-then-upsert
  idempotency (81057 race handled), idempotent delete (81044 → noop), mapped
  errors (`CLOUDFLARE_AUTH_FAILED`, `CLOUDFLARE_PERMISSION_DENIED`,
  `CLOUDFLARE_RATE_LIMITED` + retry-after, `CLOUDFLARE_DNS_CONFLICT`,
  `CLOUDFLARE_UNAVAILABLE`), plus an in-memory fake and a fixture provider for
  E2E. Namespace guard rejects anything outside `d-*.<zone>` before any
  transport call; ACM validation records are written under
  `<label>.d-<id>.<zone>` only, unproxied.
- **DNS reconciliation** — the default-HTTPS machine
  (`apps/api/src/default-https.ts`) upserts both records on install/heartbeat,
  records `lastDnsCheckAt`/`lastError`, and is bounded by a watchdog
  (`MAX_DEFAULT_HTTPS_CONFIGURE_CYCLES = 5`; rate-limited attempts consume no
  budget). Failures are state-only and never recreate AWS resources.
- **HTTPS verification** — `DomainCheckDeps.probeHttps` returns
  `{ok, reason}` (DNS/TLS/cert/timeout/404/500 reasons); ACTIVE only on a
  healthy probe. READY = `healthStatus HEALTHY` + an https URL; no custom
  domain required.
- **Fallback** — the default URL is never disabled while a custom domain
  exists; every custom failure/pending/removed state serves the default URL.
- **Cleanup** — destroy, force-complete, and purge paths delete both default
  records; purge additionally reconciles orphaned `d-*` records whose
  deployment row is gone; guarded names are skipped with zero provider calls.
- **Origin TLS** — browser → Cloudflare edge (HTTPS), Cloudflare → ALB over
  the per-deployment ACM cert installed on the 443 listener by the relay
  (Full (strict) is the correct zone mode; if the zone stays Flexible the
  origin hop is plain HTTP — documented limitation, `docs/mvp-default-https-status.md`).

## Known Limitation

The first production execution of the feature will be the first real
Cloudflare provider-path validation. All provider behavior was verified
through mocks and simulated E2E only; the real-zone write path (auth, zone
permissions, record upsert, proxied routing) is exercised for the first time
when a real customer deployment invokes it. Operational follow-ups: confirm
the zone SSL/TLS mode is Full (strict) out-of-band, and observe the first
real reconciliation via `default_https.lastError`/`lastDnsCheckAt` and the
watchdog states.
